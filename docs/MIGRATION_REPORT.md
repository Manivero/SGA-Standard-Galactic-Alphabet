# MIGRATION REPORT — слияние SGA FINAL_PROJECT (Раунд 1) + structs/stdlib-ветка → итоговый канонический репозиторий (Раунд 2)

Этот отчёт описывает **второй раунд слияния**, выполненный в этой
сессии: объединение уже смерженного проекта (Раунд 1, см. приложение
ниже — closures + modules + gradual typing + ownership/borrowing) со
**второй, отдельной** веткой репозитория (архив `SGA-final.zip`,
каталог `SGA-Standard-Galactic-Alphabet-main`), которая развивалась
независимо и принесла **структуры (struct)** и **расширенную
стандартную библиотеку** (18 builtin-функций), но не содержала
typechecker и ownership-модель.

Все утверждения ниже — результат реальных `cargo build`/`cargo
test`/`cargo run`, выполненных в процессе слияния, включая четыре
критических дефекта входной ветки, найденных **только эмпирически**
(текстовый дифф их не показывал).

## 0. Что на самом деле представляли собой входные данные этого раунда

- **База (далее A)** — `sga-final-fused.zip` → каталог `FINAL/`.
  Результат Раунда 1: lexer/parser/AST/semantic/codegen/vm/runtime +
  градуальная типизация + Ownership/Borrowing (`MUT`) + closures +
  модули (`IMPORT`). 65/65 тестов, 0 warning. Алфавит — **реальный**
  зарегистрированный UCSUR-блок `U+EB40`, с шрифтом Fairfax HD в
  репозитории.
- **Донор (далее B)** — `SGA-final.zip` → каталог
  `SGA-Standard-Galactic-Alphabet-main/`. Отдельная линия разработки
  того же языка: тот же lexer/parser/AST/semantic/codegen/vm/runtime
  (общий предок с A — `module_resolver.rs` и `main.rs` побайтово
  идентичны), но: (1) структуры (struct) с методами по конвенции
  `TypeName_method(self,...)`, реализованные ПОЛНОСТЬЮ (parser → AST →
  semantic → codegen → VM); (2) 18 builtin-функций вместо 5
  (range/keys/sqrt/floor/ceil/abs/min/max/pow/str_*/type_of); (3) НЕТ
  typechecker, НЕТ ownership/`MUT`; (4) алфавит — **самодельная** PUA-
  область `U+F100`, шрифт `sga.ttf` заявлен в README, но физически
  отсутствует в репозитории.

В A токен `STRUCT` был объявлен в лексере, но НЕ ИМЕЛ парсера/AST/
codegen/VM — мёртвая, на 0% реализованная фича (`grep -rn "Struct"
src/` за пределами `token.rs` не находил ни одного совпадения).

## 1. Критические дефекты ветки B, найденные ТОЛЬКО эмпирически

Текстовый анализ и дифф не показывали ничего из этого — обнаружено
только после установки `rustc`/`cargo` в среде и реальной компиляции:

1. **`src/runtime/mod.rs:248`** — `write!(f, "{}: ")?;` без аргумента
   для `{}` → `error: 1 positional argument in format string, but no
   arguments were given`. Библиотека **не компилировалась вообще**.
2. После фикса (1) — **новая** ошибка: `src/semantic/mod.rs:381` —
   нарушение borrow checker'а (`self.structs.get(...)` держит immutable
   borrow через вызов `self.check_expr(...)`, которому нужен `&mut
   self`) → `E0502`.
3. После фиксов (1)+(2) библиотека собирается, но **тестовый набор —
   нет**: `Value` выводит только `derive(Debug, Clone)`, не
   `PartialEq`, а все 58 тестов используют `assert_eq!` → **20 ошибок
   компиляции**. Заявленные "58 passing tests" ни разу реально не
   запускались.
4. **Найдено уже после исправлений (1)-(3), при попытке перенести
   FieldAccess в A**: добавление безусловного `Dot`-перехода в
   `parse_postfix` (как в исходном коде B) ломает `FOR i IN a..b {...}`
   — `parse_expr()` для границы диапазона жадно потребляет первый `.`
   как начало FieldAccess, затем падает на втором `.`. Эмпирически
   подтверждено прямым вызовом `sga::run_source()` на исправленной
   копии B: `FOR i IN 0..3 {...}` даёт `Lex`-ошибку. Поскольку
   собственный тестовый набор B никогда не компилировался (см. п.3),
   эта регрессия в FOR-циклах — фиче, общей с A — никогда не была
   обнаружена.

Дефекты (1)-(3) исправлены ЛОКАЛЬНО в копии B только для того, чтобы
эмпирически проверить корректность переносимой ЛОГИКИ (вызовом
`sga::run_source()` напрямую, в обход сломанного `assert_eq!`-набора).
После проверки сама логика structs/methods/stdlib подтверждена
корректной: `Point{x:3,y:4}` → `p.x+p.y=7`; метод `Point_move(self,dx,dy)`
корректно мутирует поля через `self`; `range(3)→[0,1,2]`,
`sqrt(16.0)→4`, `str_upper("abc")→"ABC"`, `type_of(5)→"int"`. Дефект (4)
исправлен НЕ копированием, а заменой решения (см. §3).

| Конфликт | Последствие | Решение | Причина |
|---|---|---|---|
| Алфавит: `U+EB40` (A, реальный UCSUR) vs `U+F100` (B, самодельный PUA, шрифт отсутствует) | Исходники A и B бинарно несовместимы на уровне символов | Оставлен **A** (`U+EB40`) | Реально зарегистрированный блок + реальный шрифт в репозитории; у B шрифт даже не существует |
| `Struct`-токен жив в B, мёртв в A | Слепое копирование кода B унаследовало бы регрессию FOR-циклов (см. п.1.4) | Грамматика `parse_postfix` переписана: лукахед `next_is_dot()` отличает одиночный `.` (FieldAccess) от `..` (диапазон) | Минимальное, точечное исправление вместо переноса баги "как есть" |
| Structs — reference-тип, но без ownership-модели в B | Структуры были бы единственной "дырой": мутация поля через `LET`-переменную в обход всей ownership-модели A | `FieldAssign` теперь проходит `check_mutation_target`; `mutation_root` расширен на `Expr::FieldAccess` (рекурсивно, как `Expr::Index`) | Согласованность с уже существующей моделью для массивов — не оставлять класс типов вне правил |
| `values_equal` в A: `_ => false` для `Array` (отсутствовала identity-equality) | `let a=[1]; let b=a; a==b` давало `ложь` — реальная регрессия в A, не связанная со слиянием напрямую, но найденная при переносе той же логики для `Struct` из B | Добавлена `Rc::ptr_eq`-эквивалентность для `Array` (фикс существующего дефекта A) и `Struct` (перенос из B) | Используется единая, согласованная семантика identity-equality для всех reference-типов |
| `is_builtin`/`call_builtin`: 5 функций (A) vs 23 (B, включая структуры) | — | Объединено: 23 функции, ошибки через `type_display_name()` (показывает реальное имя struct-типа) | Чистое объединение, не конфликт |
| `Value` без `derive(PartialEq)` в B (см. п.1.3) | — | Не актуально для A: `Value` в A уже выводит `PartialEq` (исправлено в Раунде 1) | Унаследовано из A, фикс B не нужен |

## 3. Что взято откуда

**Из A (база, без изменений):** lexer, lexer/token (кроме STRUCT —
оживлён), AST для типов/ownership/closures/modules, semantic-анализ
типов/ownership/closures/modules, typechecker целиком, VM
ownership-defense-in-depth (`param_mut`), module_resolver, CLI,
VS Code расширение со шрифтом, translit-инструмент (реюз crate'а).

**Из B (перенесено и адаптировано):** AST-узлы `StructLit`/
`FieldAccess`/`FieldAssign`/`MethodCall`/`StructDecl`; `Value::Struct`;
opcodes `MakeStruct`/`GetField`/`SetField`/`CallMethod`; 18 stdlib-
функций (`type_of`, `keys`, `range`, `sqrt`, `floor`, `ceil`, `abs`,
`min`, `max`, `pow`, `str_split`, `str_contains`, `str_trim`,
`str_starts_with`, `str_ends_with`, `str_replace`, `str_upper`,
`str_lower`); `type_display_name()`.

**Переписано (не перенесено "как есть"):**
- `parse_postfix`: добавлен лукахед `next_is_dot()` — в B такого не
  было, это НОВОЕ решение, устраняющее найденный конфликт грамматик.
- `semantic::check_expr` для `FieldAssign`: добавлен вызов
  `check_mutation_target` — в B такого не было (там не было ownership
  вообще).
- `semantic` для `StructLit`: клонирование набора полей перед циклом
  (`declared.clone()`) вместо удержания `&self.structs` через
  `check_expr(&mut self)` — фикс дефекта (2) из §1, а не перенос кода
  B как есть.
- `fmt_value` для `Value::Struct`: добавлен аргумент `k` в
  `write!(f, "{}: ", k)` — фикс дефекта (1) из §1.
- `typechecker`: новые `Expr`/`Stmt`-ветки для structs не существовали
  в B (там не было typechecker'а) — написаны заново, типизируют
  structs как `Any` (нет `TypeAnnotation::Struct` в v0.1).

**Удалено:** ничего из функциональности — только дублирующиеся
константы/мёртвый код, как и в Раунде 1 (см. приложение, §4).

## 5. Известные ограничения, перенесённые/сохранённые осознанно

- Call-site borrow-checking для `MUT self` в `.method()`-вызовах
  (что `obj` обязан быть `var`-связанным, если вызываемый метод
  объявлен с `MUT self`) **не выполняется статически** — имя функции
  (`TypeName_method`) зависит от рантайм-типа `obj`, которого semantic
  не знает (структуры не участвуют в статической системе типов v0.1).
  Защита всё же есть на уровне ТЕЛА метода: без `MUT self` присваивание
  `self.field = ...` внутри метода отклоняется той же проверкой, что и
  для обычных параметров (см. тест
  `test_struct_method_call_without_mut_self_cannot_mutate_field`).
  См. docs/ROADMAP.md.
- `pow(base, exp)` для `Int`-экспонент использует `exp as u32` —
  экспоненты `> u32::MAX` теперь явно отклоняются с понятной ошибкой
  (это ужесточение относительно исходного кода B, где такой `exp`
  тихо обрезался бы битовым усечением).

## 0. Что на самом деле представляли собой PROJECT_A и PROJECT_B

Это не два независимо написанных репозитория "с нуля" — это два
расходящихся состояния ОДНОГО проекта:

- **PROJECT_B** (`sga-lang-v0_5_0.zip`) — полный, самодостаточный

  `/mnt/user-data/outputs/sga-patched/...` — рабочую директорию другого
  ИИ-инструмента). В нём: те же модули, что и в B, но с убранной
  типизацией/Ownership и добавленными **замыканиями** + **модулями

  Доказательство: построчный diff `ast/mod.rs`, `lib.rs`, `token.rs`

Практическое следствие для слияния: это не "выбрать лучшую из двух
реализаций одной фичи" (как в типичном merge-конфликте), а
**объединить две ортогональные фичи, одна из которых была принесена в
жертву другой без необходимости** (см. §2).

## 2. Главный найденный конфликт: `MUT` vs `IMPORT` — и почему это псевдоконфликт

В A токен `MUT` был **заменён** на `IMPORT` в той же позиции
`token.rs::keyword_from_mnemonic`, а `Param.mutable`/`FunctionDef.param_mut`
удалены из структур данных — вместе с этим **повторно открылась дыра**,
которая в B была явно найдена и закрыта (см. `docs/SECURITY.md` в B):
`vm::call` в A привязывал КАЖДЫЙ параметр функции как `(значение, true)`
независимо от сигнатуры — то есть `let frozen = [...]; mutate(frozen);`
снова мог незаметно мутировать `frozen` через тело `mutate`, даже если
параметр не объявлен `MUT` (в A эта проверка просто не существовала).

Эта замена была **не нужна архитектурно**: `src/sga_alphabet.rs`
определяет полный 26-буквенный алфавит (каждая ASCII-буква A-Z -> один
SGA-кодпоинт), а не таблицу с фиксированным числом слотов под конкретные
ключевые слова — ключевое слово — это просто строка, найденная в
match-выражении `keyword_from_mnemonic`. Добавление `IMPORT` не требовало
удаления `MUT`; это видно непосредственно по циклу декодирования в
`src/lexer/mod.rs` (накопление подряд идущих SGA-букв в строку, затем
поиск этой строки в таблице) — там нет ничего, что ограничивало бы
число или длину различимых слов.

**Решение:** оба токена восстановлены одновременно (`TokenKind::Mut` и
`TokenKind::Import`), `Param.mutable`/`FunctionDef.param_mut` восстановлены
полностью, `vm::call` снова привязывает параметр с флагом из сигнатуры.
Добавлен тест `test_vm_enforces_param_immutability_even_if_semantic_is_bypassed`,
который проверяет защиту НАПРЯМУЮ на уровне VM через сконструированный
байткод (минуя `semantic`), чтобы повторное открытие именно этой дыры
было обнаружено даже при будущей регрессии на уровне semantic-анализа.
Добавлен тест `test_mut_parameters_and_closures_coexist_in_same_program`,
доказывающий отсутствие конфликта эмпирически, а не только текстом.

## 3. Баги, найденные ТОЛЬКО благодаря фактической пересборке (не текстовым ревью)

Ничего из перечисленного ниже не было известно до того, как репозиторий
был реально собран (`cargo build`) и протестирован (`cargo test`) —
в этом окружении это стало возможным после установки `rustc`/`cargo`
(в окружении разработки исходных веток их, судя по их собственным
комментариям и по характеру багов ниже, не было).

### 3.1. Тестовый набор A не компилировался

`tests/integration_test.rs` (ветка A) использовал
`assert_eq!(run(&src).unwrap(), Value::Int(5))` в тестах на замыкания,
но `runtime::Value` не реализовывал `PartialEq` — компиляция тестов
падала. Отдельно, тест на глубину рекурсии перемещал
`Result<Value, SgaError>` через границу потока (`std::thread::spawn`),
хотя `Value`/`SgaError` содержат `Rc<...>` (не `Send`) — тоже ошибка
компиляции. **Исправлено**: `PartialEq` добавлен на `Value`/`Chunk`/
`OpCode`/`ClosureValue`; тест на рекурсию теперь конвертирует результат
в `Result<(), String>` (только примитивы) до пересечения границы потока.

### 3.2. После фикса (3.1) тесты на замыкания провалились по значению, не по компиляции

`let f = FN(x){...}; f(1);` как программа: последний statement —
`ExprStmt`, который `codegen::compile_stmt` всегда завершает `Pop`
(значение отбрасывается), а конец `main`-чанка — безусловный
`Return(false)` (`Nil`). Поэтому `run_source()` для такой программы
ВСЕГДА возвращал `Value::Nil`, что и показал реальный прогон:
`test_closure_basic_call_through_variable` ожидал `Int(5)`, получил...
(см. 3.3 — там результат оказался ещё более показательным, чем просто
`Nil`). **Исправлено**: добавлен `Compiler::compile_tail_stmt` —
значение ПОСЛЕДНЕГО top-level `ExprStmt` программы становится
результатом `Vm::run` через `Return(true)`, а не отбрасывается. Это не
костыль "чтобы тест прошёл", а осмысленная семантика
("скрипт возвращает значение своего последнего выражения" — как REPL
большинства динамических языков), задокументированная в
`docs/COMPILER_SPEC.md`.

### 3.3. Грамматическая дыра в IIFE, скрытая до фикса 3.2

После фикса 3.2 тест `test_closure_iife_as_statement`
(`FN(x){ RETURN x*2; }(21);`, ожидание `42`) вернул `21`, а не `Nil` и
не `42`. Причина: `parser::parse_postfix` обрабатывал постфиксом только
`[idx]`, а вызов `(args)` — только для bare-идентификатора, разобранный
ВНУТРИ `parse_primary`. Лямбда-литерал, разобранный в `parse_primary`,
возвращался наверх БЕЗ потребления следующего за ним `(21)` — токены
`(21);` оставались непрочитанными и на следующей итерации
`parse_program` ошибочно разбирались как ВТОРОЙ, независимый top-level
statement (`(21);`, просто скобки вокруг литерала). После фикса 3.2 этот
второй statement стал "хвостовым" и вернул `21` — то есть один баг
(грамматическая дыра) маскировался другим (отбрасывание хвостового
значения, см. 3.2) до тех пор, пока вместе они не дали "случайно
похожий, но неверный" результат, а раздельное исправление одного из них
обнажило второй. **Исправлено** архитектурно, не точечным патчем:
введён `ast::Expr::CallExpr(Box<Expr>, Vec<Expr>)` — вызов ПРОИЗВОЛЬНОГО
выражения (не только статического имени), `parser::parse_postfix`
обрабатывает `(args)` как общий постфикс для любого `primary`, `codegen`
компилирует его через уже существующий `OpCode::CallValue` (тот же
механизм, что и вызов замыкания через переменную). Добавлен тест на
обобщённый случай — цепочку вызовов `make_adder(5)(1)`.

### 3.4. `max_call_depth = 2000` не успевал сработать до реального stack overflow

Тест на глубину рекурсии (после фиксов 3.1) при размере стека потока
8 МиБ и 16 МиБ завершался **аварийно** (`SIGABRT`, реальный stack
overflow процесса) — управляемая `RuntimeError` не успевала сработать.
Значение `2000` было унаследовано из B без изменений и без
эмпирической проверки. **Исправлено**: значение снижено до `200`,
эмпирически подтверждено безопасным при 8 МиБ (типичный `ulimit -s` на
Linux) добавленным тестом
`test_recursion_depth_limit_is_safe_under_default_sized_stack`; в
`docs/SECURITY.md` зафиксирована таблица замеров и оговорка про
платформо-/профиль-зависимость точного числа.

### 3.5. `tools/translit` генерировал файлы, которые компилятор не распознаёт

В A константа `SGA_BASE` в `tools/translit/src/main.rs` была изменена
с `0xEB40` (правильно, совпадает с `src/sga_alphabet.rs`) на `0xF100`
(несуществующий в проекте диапазон — судя по всему, по той же ошибочной
причине, по которой устаревший комментарий "U+F100..U+F119" встречается
и в других файлах A, например `module_resolver_test.rs`). Это
подтверждено эмпирически: оригинальный `translit/src/main.rs` из A был
собран как отдельный бинарник и запущен на реальном примере проекта
(`examples-src/hello.sga.src`) — результат не прошёл лексер итогового
компилятора (`ошибка лексера: неожиданный символ '' (U+F10B)`).
**Исправлено** не точечной правкой константы, а структурно: и `main.sga`-
кодирование (`encode_word`), и распознавание ключевых слов
(`keyword_from_mnemonic`) теперь импортируются из основного крейта `sga`
через path-зависимость, а не дублируются — повторение этого класса
багов ("транслитератор и компилятор расходятся в кодировании")
становится структурно невозможным. Также исправлен сам устаревший
комментарий про диапазон кодпоинтов.

## 4. Что было удалено

Не было ни одного случая "выбрали A, удалили B-реализацию той же фичи
целиком" — фичи из A и B оказались дополняющими, а не конкурирующими
(см. §2). Удалено только:

- Дублирующиеся константа `SGA_BASE` и список ключевых слов в
  `tools/translit` (заменены на реальную зависимость от `sga`, см. 3.5).
- Хардкод `(значение, true)` в `vm::call` (вместо него — `param_mut`).
- Устаревшие/неверные упоминания диапазона кодпоинтов
  `U+F100..U+F119` в комментариях.

## 5. Итоговая проверка

`bash scripts/build.sh` (полная официальная сборка проекта: `sga` +
`sga-translit` + `cargo test`) проходит целиком: 0 warning'ов при
компиляции, **65/65** тестов зелёные (56 интеграционных +
9 модульных). Все 10 файлов в `examples/` реально выполнены через
`target/release/sga run` (включая 4 новых, демонстрирующих совместную
работу типов/Ownership/замыканий/модулей). `tools/translit` пересобран
и проверен round-trip на реальном примере (вывод побайтово совпадает с
ранее закоммиченным `examples/hello.sga`).
