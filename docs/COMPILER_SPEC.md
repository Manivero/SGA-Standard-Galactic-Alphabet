# COMPILER SPEC — SGA v0.1

## Пайплайн

```
исходный .sga текст (+ путь к файлу, для IMPORT)
   │
   ▼  src/lexer/mod.rs
Vec<Token>            — SGA-кодпоинты декодируются в ключевые слова,
   │                     ASCII — в идентификаторы/литералы/операторы
   ▼  src/parser/mod.rs
AST (src/ast/mod.rs)  — рекурсивный спуск, операторные приоритеты
   │                     (включая Lambda-выражения и IMPORT-statement)
   ▼  src/module_resolver.rs   (только sga::run_source_file; программа без
   │                            IMPORT проходит без изменений — см. ниже)
AST без IMPORT        — top-level statement'ы импортированных файлов
   │                     инлайнятся рекурсивно; циклы/диамант-импорты
   │                     обработаны явно (ошибка цикла / дедупликация)
   ▼  src/semantic/mod.rs
проверенный AST       — неизменяемость, неопределённые имена,
   │                     break/continue/return в корректном контексте,
   │                     Ownership/Borrowing (MUT-параметры),
   │                     арность builtin'ов, область видимости замыканий
   ▼  src/typechecker/mod.rs
проверенный AST       — градуальная статическая типизация (только там,
   │                     где есть явная аннотация `: тип`)
   ▼  src/optimizer.rs           (T010, M004)
оптимизированный AST  — constant folding + dead code elimination;
   │                     семантически прозрачен (работает НАД уже
   │                     проверенным AST — недостижимый код по-прежнему
   │                     был проверен строкой выше, до своего удаления)
   ▼  src/codegen/mod.rs
CompiledProgram        — { main: Chunk, functions: HashMap<String, FunctionDef> }
   │                     каждая функция/замыкание — отдельный Chunk с
   │                     backpatched адресами переходов
   ▼  src/vm/mod.rs
Vm::new(...)           — bytecode verifier (индексы констант, цели
   │                     переходов, рекурсивно для тел замыканий)
   ▼
Vm::run(&chunk)        — стековый интерпретатор байткода -> Value
```

`sga::run_source(text)` — конвейер БЕЗ файлового контекста; `IMPORT` в
такой программе — явная ошибка (нет базовой директории для резолвинга
путей). `sga::run_source_file(path)` — полный конвейер с
`module_resolver`, см. `src/lib.rs`. Обе функции запускают программу с
параметрами по умолчанию; параметры запуска (T012/T013, M006: аргументы
командной строки для `args()` и источник стандартного ввода для
`read_line()`/`read_stdin()`) передаются через
`sga::run_source_with_options(text, RunOptions)` и
`sga::run_source_file_with_options(path, RunOptions)`. `RunOptions` —
builder (`RunOptions::new().with_args(..)`, `.with_stdin_bytes(..)`,
`.with_process_stdin()`); параметры попадают в VM через `Vm::set_args` и
`Vm::set_stdin` между `Vm::new` и `Vm::run`. По умолчанию ввод ПУСТ:
стандартный ввод процесса библиотека не трогает, пока его явно не
подключили (`with_process_stdin()`, так делает CLI).

## Lexer (`src/lexer/mod.rs`)

Однопроходный сканер по `Vec<char>`. SGA-кодпоинт (U+EB40..U+EB59)
запускает накопление "слова" из подряд идущих SGA-букв, которое
декодируется (`sga_alphabet::decode_word`) и ищется в таблице ключевых
слов (`token::keyword_from_mnemonic`). Если слово не найдено — лексер
возвращает `LexError` (не "молча" принимает произвольный SGA-текст как
идентификатор — в языке нет SGA-идентификаторов, только ключевые слова).

## Parser (`src/parser/mod.rs`)

Классический рекурсивный спуск с явной таблицей приоритетов операторов
(`assignment -> or -> and -> equality -> comparison -> term -> factor ->
unary -> postfix -> primary`). Узлы AST — `ast::Stmt` / `ast::Expr`
(`src/ast/mod.rs`).

## Semantic Analyzer (`src/semantic/mod.rs`)

Два прохода:
1. Сбор сигнатур функций верхнего уровня — арность **и** флаг `MUT` для
   каждого параметра (`FnInfo { arity, mut_params }`) — позволяет
   взаимные/опережающие вызовы и проверку Ownership/Borrowing на месте
   вызова.
2. Рекурсивный обход AST со стеком областей видимости
   (`Vec<HashMap<String, bool>>`, `bool` = mutable), проверяющий:
   - повторное объявление в одной области видимости;
   - использование неопределённого имени;
   - присваивание immutable-переменной (включая глубокую мутацию
     массивов через индекс/`push`, см. `check_mutation_target`);
   - корректную арность вызовов известных функций **и** builtin'ов
     (`len`/`push`/`to_string`/`to_int`/`to_float` — у `push` диапазон
     1..=2, у остальных ровно 1; раньше арность builtin'ов не
     проверялась вовсе — несогласованность с проверкой пользовательских
     функций, закрыта при слиянии, см. `docs/MIGRATION_REPORT.md`);
   - **Ownership/Borrowing**: параметр без `MUT` объявляется в scope
     функции с `mutable=false` — любая попытка его мутировать (как
     обычной immutable-переменной) отклоняется тем же механизмом, что
     и `LET`. На месте вызова: если параметр объявлен `MUT`, аргумент
     должен резолвиться (через `mutation_root`) к переменной, объявленной
     `VAR` — иначе ошибка компиляции. Применяется ТОЛЬКО к статически
     известным top-level функциям — у вызова через переменную
     (`Expr::Call` с `name`, не входящим в таблицу функций) и у
     `Expr::CallExpr` (вызов произвольного выражения, см. ниже) нет
     статической сигнатуры для borrow-checking; несоответствие арности
     там — `RuntimeError`, обнаруживаемая в `vm::call_value`;
   - **замыкания** (`Expr::Lambda`): тело проверяется в НОВОЙ scope для
     параметров (всегда `mutable=true`, без `MUT`-аннотаций), поверх
     текущего стека scope — без копирования, для корректной лексической
     видимости захватываемых переменных; `loop_depth` обнуляется и
     восстанавливается вокруг проверки тела (чтобы `BREAK` внутри
     замыкания, созданного в цикле, корректно считался "вне цикла" —
     замыкание исполняется в собственном вызове VM, а не в потоке
     управления цикла), `fn_depth` инкрементируется (RETURN внутри
     замыкания корректен);
   - **`Expr::CallExpr`** (вызов произвольного выражения — IIFE,
     `f()()`, и т.п.): callee и аргументы проверяются рекурсивно, без
     статической арности/borrow-checking — та же логика, что и для
     `Expr::Call` через переменную;
   - `break`/`continue` только внутри `loop_depth > 0`;
   - `return` только внутри `fn_depth > 0`.

## Typechecker (`src/typechecker/mod.rs`)

Отдельный проход после `semantic`, до `codegen`. Градуальная
(опциональная) статическая типизация: проверяется только то, что явно
аннотировано (`: int`, `-> string`, ...) — всё остальное трактуется как
`Any` и не проверяется (нулевая обратная несовместимость с untyped-кодом).
Поддерживает: проверку инициализаторов `LET`/`VAR`/`CONST` против
аннотации, проверку аргументов вызова против сигнатуры функции (включая
встроенные `len`/`push`/`to_string`/`to_int`/`to_float`), проверку
`RETURN` против заявленного типа возврата функции, вывод типа бинарных
операций (с авто-повышением `int -> float`, согласованным с
`vm::arith`). Типы стираются сразу после этого прохода — `codegen` и
`vm` про `TypeAnnotation` ничего не знают. `Expr::Lambda` типизируется
как `Closure` без проверки сигнатуры (параметры — `Any`, тело
проверяется в новой scope); `Expr::CallExpr` ожидает `Closure`/`Any` у
callee и возвращает `Any` (сигнатура замыкания не отслеживается).

**Не реализовано**: типы элементов массива (generics), типы полей
структур (структур нет), union/intersection-типы, типизированные
сигнатуры замыканий — см. `docs/ROADMAP.md`.

## Codegen (`src/codegen/mod.rs`)

AST -> `Chunk { code: Vec<OpCode>, constants: Vec<Value> }` (типы
байткода определены в `src/runtime/mod.rs`, не здесь — см. примечание
в исходнике о причине: `Value::Closure` хранит `Rc<Chunk>`, и обратная
зависимость `runtime -> codegen` дала бы цикл модулей; `codegen`
ре-экспортирует их для обратной совместимости публичного API). Каждая
top-level функция компилируется в свой `Chunk` отдельным `Compiler`;
каждое `Expr::Lambda` — аналогично, в момент компиляции выражения, и
упаковывается в `OpCode::MakeClosure { params, body: Rc<Chunk> }` прямо
в потоке инструкций (у замыкания нет статического имени, поэтому оно не
попадает в `CompiledProgram::functions`).

Вызов по статическому имени (`name` входит в `known_functions` —
множество top-level функций, собранное первым проходом — или
является builtin) компилируется в `OpCode::Call(name, argc)`. Любой
другой вызов (через переменную, IIFE, цепочку вызовов) компилируется
через `LoadVar`/произвольное выражение-callee + `OpCode::CallValue(argc)`
— callee снимается со стека динамически в VM.

Значение ПОСЛЕДНЕГО top-level `Stmt::ExprStmt` программы (если такой
есть) становится результатом `Vm::run`/`sga::run_source` — не
отбрасывается оператором `Pop`, как любой другой expression-statement
(см. `compile_tail_stmt`). Это нужно, чтобы `let f = ...; f(1);` как
программа возвращало значение вызова, а не всегда `Nil` — см.
`docs/MIGRATION_REPORT.md` про обнаружение этого при слиянии.

Условные переходы и циклы реализованы через классический **backpatching**:
эмиттируется `Jump`/`JumpIfFalse` с временным адресом 0, индекс позиции
запоминается, после компиляции тела реальный адрес записывается обратно
(`patch_jump`). `break`/`continue` используют тот же механизм через
`LoopCtx { break_patches, continue_patches }` в стеке активных циклов.

Полный список опкодов — `docs/VM_SPEC.md`.

## VM (`src/vm/mod.rs`)

Стековый интерпретатор. Каждый вызов top-level функции или замыкания
выполняется **рекурсивным** вызовом `run_chunk` со свежим стеком
значений; стек областей видимости для замыкания инициализируется ДВУМЯ
scope — снимком захваченного окружения (`ClosureValue::captured`) и
поверх него — новой scope с параметрами текущего вызова (см.
`Vm::call_value`). `Return` — не переход, а немедленный выход из
`run_chunk` с результирующим `Value`.

Перед началом исполнения `Vm::new` верифицирует байткод
(`verify_program`/`verify_chunk`) — проверяет индексы `PushConst`
против пула констант и цели `Jump`/`JumpIfFalse` против длины чанка,
рекурсивно для тел всех замыканий (`OpCode::MakeClosure`). Это
defense-in-depth для случая, когда `Chunk`/`CompiledProgram`
сконструированы вручную в обход `codegen::compile()` (оба типа
публичны) — без верификации некорректные индексы давали бы Rust panic
вместо управляемой `RuntimeError`.

## Optimizer (`src/optimizer.rs`, T010/M004, 2026-08-18)

AST -> AST проход, между `typechecker` и `codegen` (НЕ между `codegen` и
`vm`, как предполагалось раньше в этом документе, — осознанный выбор:
оптимизация на уровне AST, а не байткода, проще рассуждать о корректности
и позволяет напрямую переиспользовать типы `ast::Expr`/`ast::Stmt`).
Constant folding (арифметика/сравнения/`AND`/`OR`/унарные `-`/`NOT` на
литералах — рекурсивно, снизу вверх) + dead code elimination (код после
`RETURN`/`BREAK`/`CONTINUE`; `IF`/`WHILE` со свёрнутым в константу
условием). Семантически прозрачен: место в пайплайне — ПОСЛЕ
`typechecker`, поэтому недостижимый код по-прежнему проверяется на
ошибки ДО своего удаления. Арифметика НЕ дублируется заново —
переиспользует `vm::arith`/`vm::compare`/`vm::values_equal` (сделаны
`pub(crate)` специально для этого): если операция дала бы ошибку во
время выполнения (переполнение `Int`, деление на ноль), выражение НЕ
сворачивается — рантайм выдаёт ТУ ЖЕ ошибку, что и без оптимизатора.
`AND`/`OR` в SGA не имеют short-circuit семантики (оба операнда всегда
компилируются и вычисляются в runtime) — это упрощает их сворачивание.
Инлайнинг функций — явно ВНЕ scope T010, отдельная возможная будущая
задача.

## Module Resolver (`src/module_resolver.rs`)

Резолвит `Stmt::Import` ДО семантического анализа: путь — относительно
директории файла, в котором встретился `IMPORT` (рекурсивно для
транзитивных импортов — каждый уровень резолвится относительно СВОЕГО
файла, а не корневого). Дедупликация по каноническому пути файла
(`pragma once`-подобная семантика — diamond-импорт инлайнится один раз).
Цикл импортов — явная ошибка с указанием цепочки файлов, а не
бесконечная рекурсия резолвера. Загрузка файлов абстрагирована через
trait (`FsLoader`) — для тестов используется in-memory реализация без
обращения к реальной файловой системе (`tests/module_resolver_test.rs`).

### `pkg:`-импорты и `sga.toml` (T011, M005, 2026-10-10)

`IMPORT "pkg:имя/путь/к/файлу.sga"` — отдельная ветка `Stmt::Import` в
`resolve_program` (lexer/parser/AST не менялись: `pkg:` — просто префикс
строки). Имя пакета ищется в `[dependencies]` БЛИЖАЙШЕГО `sga.toml`:
`manifest::load_nearest` поднимается от каталога входного файла вверх по
дереву (по канонизированному абсолютному пути — иначе `sga run main.sga`
из `proj/src` упёрся бы в пустой родитель относительного пути) и берёт
первый найденный манифест целиком, без слияния с внешними.
`src/manifest.rs` — ручной мини-парсер ТОЛЬКО секции `[dependencies]`
(формат `имя = { path = "..." }`), без внешнего `toml`-крейта. Путь
зависимости считается от каталога манифеста; файл внутри пакета обязан
остаться в каталоге пакета (`is_within_root` — та же проверка, что у
обычного `IMPORT` и `read_file`, а не её копия). Контекст резолвинга
(`ResolveCtx`: `root`, `manifest`, `loader`, `parse_fn`) передаётся
неизменным вниз по рекурсии; при заходе в пакет `root` заменяется на
каталог пакета, а флаг `in_package` запрещает транзитивные `pkg:`.
Результат поиска манифеста хранится как `Result<Option<Manifest>, String>`,
и его ошибка возвращается только из ветки `pkg:` (ленивая валидация):
программы без `pkg:` не зависят от содержимого какого-либо `sga.toml`.

## Тесты

`tests/integration_test.rs` (184 теста) + `tests/module_resolver_test.rs`
(12 тестов) + 26 unit-тестов лексера + 4 unit-теста json + 17 unit-тестов optimizer + 17 unit-тестов manifest + 14 unit-тестов stdin (`src/lexer/mod.rs`, `src/json.rs`, `src/optimizer.rs`, `src/manifest.rs`, `src/stdin.rs`) — через публичный API `sga::run_source()`/`run_source_file()`,
проверяющих как успешные программы (арифметика, рекурсия, циклы, массивы,
типизированный и смешанный typed/untyped код, `MUT`-параметры, замыкания,
IIFE, цепочки вызовов, импорты, диамант-импорты), так и обязательные
отказы (immutable-запись, overflow, деление на 0, OOB, undefined-имя,
break вне цикла, несовпадение типов, передача `LET` в `MUT`-параметр,
вложенный `FN`, неверная арность builtin'а, цикл импортов). Отдельно —
тесты на bytecode verifier (повреждённый байткод, сконструированный
напрямую в обход `codegen::compile()`) и на безопасность
`max_call_depth` при реалистичном размере стека потока (см.
`docs/SECURITY.md`). Запуск: `cargo test`.
