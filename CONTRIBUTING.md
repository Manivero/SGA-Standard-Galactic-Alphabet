# Contributing to SGA

## Сборка и тесты

```bash
cargo build               # компилятор + VM
cargo test                # 876 тестов (247 интеграционных + 13 модульных + 24 сквозных теста языкового сервера + 9 тестов подсказок сервера и больших документов (сверка с компилятором, словарь исполнением, устойчивость) + 12 тестов навигации сервера (сверка с настоящим AST и настоящим исполнением) + 26 тестов позиций ошибок semantic/typechecker + 34 теста диапазонов узлов AST + 1 сверка диагностик с CLI + 44 unit-теста лексера + 11 unit-тестов парсера + 13 unit-тестов ast + 4 unit-теста json + 20 unit-тестов optimizer + 17 unit-тестов manifest + 14 unit-тестов stdin + 11 unit-тестов clock + 10 unit-тестов module_resolver + 20 unit-тестов fs_sandbox + 36 unit-тестов diagnostics + 5 unit-тестов runtime + 295 unit-тестов lsp + 10 unit-тестов CLI)
cargo build --manifest-path tools/translit/Cargo.toml   # инструмент транслитерации
```

Перед PR: `cargo build` должен завершаться без единого warning'а
(`cargo build 2>&1 | grep warning` — пусто), `cargo test` — все тесты
зелёные.

## Куда смотреть, если хочешь добавить фичу

| Хочу добавить... | Начинай с |
|---|---|
| Новую конструкцию синтаксиса (например `match`) | `src/lexer/token.rs` (если нужно ключевое слово — строка таблицы `keyword_table!`: из неё же берёт слова языковой сервер; **и** запись в `src/lsp/vocabulary.rs::KEYWORDS` в том же порядке — тесты сверяют состав и порядок; если слово открывает блок или шапку либо меняет области видимости — научи сканер подсказок `src/lsp/scan.rs`, иначе `tests/lsp_assist_test.rs` покажет расхождение с `semantic`) -> `src/ast/mod.rs` -> `src/parser/mod.rs` -> `src/semantic/mod.rs` -> `src/codegen/mod.rs` -> `src/vm/mod.rs`. Каждый узел AST несёт `Span` (парсер ставит `self.span_from(start)`; `tests/ast_spans_test.rs` обходит все виды узлов исчерпывающим `match` и не соберётся, пока новый вариант не описан), а ошибка `semantic`/`typechecker` указывает на узел-причину (`err_at(node.span, …)`) — иначе у ошибки не будет позиции ни в `sga run`, ни в редакторе |
| Новый встроенный тип (`map`, `set`, ...) | `src/runtime/mod.rs::Value` + везде, где `match value { ... }` бьёт по типу (компилятор подскажет через exhaustiveness check) |
| Новую встроенную функцию | `src/runtime/mod.rs`: строка `имя => (min, max)` в `builtin_registry!` (из неё выводятся `is_builtin` и `semantic::builtin_arity`) + ветка в `call_builtin` (и перехват в `Vm::call()`, если нужно состояние VM) -> описание в `src/lsp/vocabulary.rs::BUILTINS` в том же порядке (параметры, тип результата, описание) -> пример вызова в `samples()` из `tests/lsp_assist_test.rs` -> `docs/VM_SPEC.md`. Забытое подскажут тесты: состав и порядок словаря сверяются с таблицей, арность — с настоящей диагностикой компилятора, типы результата — исполнением примеров |
| Возможность языкового сервера (диагностика, hover, навигация, ...) | `src/diagnostics.rs` (что и как анализировать, без исполнения) -> `src/lsp/mod.rs` (метод протокола; объявляй в `initialize_result` только реализованное) -> `docs/LSP.md`; подсказки и навигация устроены так: `src/lsp/scan.rs` (токены с терпимой токенизацией и области видимости), `src/lsp/assist.rs` (hover и автодополнение без JSON), `src/lsp/nav.rs` (структура файла `documentSymbol` и переход к определению `definition` без JSON; позиции ответа — через `position::LineTable`, а не вызовом `to_lsp` на каждую позицию, иначе большой документ даёт квадратичное время), `src/lsp/vocabulary.rs` (русские описания слов и builtin); `tests/lsp_nav_test.rs` сверяет `definition` с настоящим исполнением программ, а `documentSymbol` — с настоящим AST, поэтому новая конструкция, которая объявляет имена или открывает область видимости, должна попасть в `scan.rs` — иначе эти тесты покажут расхождение; новая конструкция синтаксиса сама попадает в диагностики через лексер, парсер, `semantic` и `typechecker` (сервер вызывает те же стадии, что и `sga run`, до исполнения) |
| Изменение в таблице SGA-алфавита | `src/sga_alphabet.rs` — **и** `tools/translit/src/main.rs` (дублирует таблицу намеренно, чтобы инструмент оставался независимым однобинарным CLI; при изменении синхронизируй оба файла и `docs/SGA_ALPHABET.md`) |

## Правила honesty, принятые в этом проекте

Эти правила были применены при первоначальной разработке и обязательны
для дальнейших вкладов:

1. **Не объявляй фичу готовой, если она не покрыта тестом или ручной
   проверкой через `cargo run -- run <файл>`.** Если фича частично
   реализована — это явно отражается в `docs/ROADMAP.md`, а не в
   комментарии `// TODO` внутри кода, который легко не заметить.
2. **Любое утверждение про безопасность в `docs/SECURITY.md` должно быть
   подтверждено тестом.** Если нашёл реальную уязвимость/краш при
   разработке — фиксируй её в коде, а не только описывай как
   "ограничение". (Пример: `MAX_DISPLAY_DEPTH` в `src/runtime/mod.rs` —
   реальный баг с stack overflow на самореференцирующихся массивах был
   найден и исправлен, не просто упомянут.)
3. **Не копируй >30% синтаксиса существующего языка.** При добавлении
   конструкции — сверься с философией в `docs/LANGUAGE_SPEC.md`, §1.

## Структура коммитов

Один логический шаг пайплайна — один коммит, где возможно (например,
"добавить токен MATCH" отдельно от "добавить парсинг match-выражения"),
чтобы `git bisect` оставался полезным при поиске регрессий в компиляторе.
